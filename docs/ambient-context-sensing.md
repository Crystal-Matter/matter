# Ambient Context Sensing (Matter 1.6 provisional)

`Matter::Cluster::AmbientContextSensing` implements revision 1 with HumanActivity (HA), HA+ObjectIdentification (OI), HA+SoundIdentification (AUD), HA+PredictedActivity (PRED), HA+OI+PRED, standalone OI, OI+PRED, standalone AUD, AUD+PRED, standalone ObjectCounting (OC), ObjectCounting+PredictedActivity (OC+PRED), ObjectCounting+ObjectIdentification (OC+OI), or OC+OI+PRED on an opt-in endpoint. The host supplies physical classifications through `observe_human_activity`, `observe_object`, `observe_sound`, or `observe_object_count`, and may supply future forecasts through `replace_predicted_activities`. Synthetic Aggregator endpoints in `examples/matter_ambient_context_device.cr` demonstrate the wire surface; they do not claim a certified sensing device type.

```crystal
alias Ambient = Matter::Cluster::AmbientContextSensing
unknown = Ambient::SemanticTag.human_activity(Ambient::HumanActivity::Unknown)
walking = Ambient::SemanticTag.human_activity(Ambient::HumanActivity::Walking)

cluster = Ambient.new(endpoint_id,
  supported_activity_tags: [unknown, walking],
  hold_time: 30_u16)
cluster.observe_human_activity(walking)
```

The server advertises the HA bit alone. `HumanActivityDetected`, `AmbientContextType`, and `AmbientContextTypeSupported` use canonical `SemanticTagStruct` wire fields. When inactive, `AmbientContextType` contains the standard Human Activity Unknown tag (namespace 0x4B, tag 0) to satisfy its nonempty list constraint. The implementation supports one active detection; writes requesting a larger `SimultaneousDetectionLimit` return `ConstraintError`. Supported tags are configured at construction and must include Unknown.

For standalone OC, the pinned 1.6 XML requires only `SimultaneousDetectionLimit`, `HoldTime`, and `HoldTimeLimits`. It defines no count, identity, or prediction attribute and no detection event for this feature map. The server therefore exposes no host count observation through this profile; add OI for live identified-object counting or PRED for crowd forecasts.

For OC+OI, configure Identified Object namespace (0x49) tags including Unknown and one concrete object. A single supported object and threshold are selected through `ObjectCountConfig` (Manage-writable and persistent). `ObjectIdentified` becomes true for a positive host count, while `ObjectCountReached` becomes true only when the selected object's count reaches the threshold. The optional `ObjectCount` attribute has stable metadata and reads null until that threshold is reached. The start event includes the count status and includes the count when reached. A zero observation or HoldTime expiry ends detection. This profile still supports only one active detection and does not advertise HA.

For standalone OI, configure Identified Object namespace (0x49) tags including Unknown and one concrete object. `observe_object(tag, true)` starts or refreshes a detection; `observe_object(tag, false)` ends that object's detection, and HoldTime expiry also ends it. The server advertises `ObjectIdentified`, `AmbientContextType`, and `AmbientContextTypeSupported` without the three OC count attributes. Start events carry the detected object tag without count fields. Only one object can be active at once. Host classification remains responsible for determining whether that object is present.

For HA+OI, configure both Human Activity and Identified Object tags, with Human Activity Unknown and Identified Object Unknown plus a concrete object tag. `AmbientContextTypeSupported` is their union (at most 50 entries). The server exposes independent `HumanActivityDetected` and `ObjectIdentified` flags. With its one-detection limit, a host observation in the other modality ends the active detection before starting the new one; each start event carries only the newly detected tag, without OC count fields. HoldTime expiry clears the active modality and restores its Unknown tag. The host owns the classification and should call `observe_human_activity` or `observe_object` as appropriate.

For AUD, configure standard Identified Sound namespace (0x4A) tags including Unknown and at least one concrete sound. `observe_sound` accepts only configured concrete tags. It sets `AudioContextDetected`, reports the sound in `AmbientContextType`, and emits the existing start event. A repeated observation refreshes HoldTime; expiry clears the flag, restores Unknown, and emits the end event. This opt-in profile supports one active sound detection, with no built-in microphone or classifier.

For HA+AUD, configure both Human Activity and Identified Sound tags, including the Unknown tag for each. `AmbientContextTypeSupported` is their union (at most 50 entries), while `HumanActivityDetected` and `AudioContextDetected` independently report the live modality. A host observation in the other modality ends the active detection before starting the new one. Each start event carries the detected semantic tag without OC count fields; HoldTime expiry clears the active flag and restores that modality's Unknown tag. No forecast field is exposed without PRED.

For HA+PRED, OI+PRED, or AUD+PRED, configure the corresponding activity, object, or sound tags and a trusted `prediction_clock` callback that returns seconds since the Matter epoch (2000-01-01 UTC), or `nil` while time is unavailable. The host supplies future `PredictedActivityStruct` entries through `replace_predicted_activities`. Each entry has start and end timestamps, one configured tag from that profile, and confidence from 0 to 100 percent. The server accepts at most 20 entries, requires each start to follow the previous end, and publishes the replacement atomically. A prediction is removed when its start time arrives; reads refresh the list, and the host can call `refresh_predicted_activities` when its clock advances to notify subscribers promptly. Loss of trusted time clears the list. OI+PRED also accepts `observe_object` for live object presence and expiry; its forecast and detection events omit OC crowd and count fields. The predictor and clock discipline remain host-owned; the synthetic fixture uses separate explicit test clocks and hooks for HA, OI, and AUD.

For HA+OI+PRED, configure both Human Activity and Identified Object tags and a trusted Matter epoch `prediction_clock`. Host forecasts may use one configured tag from either modality per entry; the server accepts ordered, future predictions and prunes them at their start time or when trusted time is unavailable. Each forecast carries `AmbientContextType` and confidence, without OC crowd fields. Live HA and OI observations retain the one-active-modality behavior of HA+OI; forecasts do not set either live detection flag.

For OC+OI+PRED, configure the OC+OI live counting profile and a trusted `prediction_clock`. Host forecasts combine a configured Identified Object semantic tag with required `CrowdDetected`, optional `CrowdCount` (1–254), timestamps, and confidence. Publish them through `replace_predicted_activities`; the list is atomically replaced and pruned when its start time arrives or trusted time is unavailable. Live counts still use `observe_object_count`, including threshold status, count-bearing start events, and HoldTime expiry. A forecast does not itself set the live count attributes.

For OC+PRED, construct `PredictedActivityStruct.crowd(start, end, detected, confidence, count)` entries and publish them through the same host forecast API. `CrowdDetected` is required, `CrowdCount` is optional and constrained to 1–254, and `AmbientContextType` is absent from each forecast. The profile exposes `PredictedActivity` and the universal attributes, without object identity, count attributes, or detection events. A forecast is removed when its start time arrives or trusted time becomes unavailable. This profile forecasts crowd presence; it does not report live object counts or identify objects.

An observation starts a detection and emits `AmbientContextDetectStarted` with the detected semantic tag. Repeated observations of that tag add HoldTime at most once in each HoldTime period without another start event. Continuous triggered time is capped at `HoldTimeLimits.HoldTimeMax`; at the deadline, the server clears detection, restores Unknown, and emits `AmbientContextDetectEnded` with the start time in POSIX milliseconds. A later observation starts a new detection. `HoldTime` is writable with Manage privilege and survives a restart; active detection and events are volatile. `HoldTimeLimits` is fixed. An application should feed the cluster only classifications backed by its own sensor and should choose HoldTime limits that fit its sensor.

The tagged Matter 1.6 XML marks `SimultaneousDetectionLimit` writable with Operate privilege and calls the end-event field `EventStartTime` (context tag 0). The connectedhomeip future errata overlay and current matter.js model instead mark the limit read-only/fixed and use `EventStartTimePos`/`EventStartTimeSys`. This server follows the tagged 1.6 XML; compatibility with that future variant is separate work.

Standalone PRED and combined feature profiles beyond HA+OI, HA+AUD, HA+PRED, HA+OI+PRED, OI+PRED, AUD+PRED, OC+PRED, OC+OI, and OC+OI+PRED are not implemented. The constructor rejects those feature maps, so their conditional attributes and events are never advertised. The tagged 1.6 XML requires at least one of HA, OC, OI, or AUD; PRED alone is invalid. OC+PRED offers crowd forecasts, and OC+OI offers live counting and identity. This provisional slice does not implement a physical sensor, classifier, or certification policy.
